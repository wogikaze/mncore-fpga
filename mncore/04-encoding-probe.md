# 04. 命令語エンコードの予備実験

> **追記（2026-11-24）: この予備実験より詳しい情報がすでにある。**
> - Scrapbox の [mncore/機械語](https://scrapbox.io/mncore/機械語) に、ほぼすべての配置が観測済みで記録されている。
>   - auto_stride（292bit）と flat（426bit）の領域の表
>   - ALUC の aluop 全 32 種と入力セレクタ
>   - MAUC の制御ビットの組み合わせ
>   - 即値 32bit の分散配置
>   - flat の PE アドレス（cycle0〜3）
>   - MV の 12 フィールド
>   - L1BM/L2BM の組み合わせ
>   - q / loader / binary のコンテナ
> - さらに、`assemble3 --print-csv` は**名前付きの全フィールド**を出力する。
>   flat の `iadd $lm0v $lr0v $ln0v` で試したところ、j 行は 110 列（ヘッダは 95 列）で幅の合計が 426 になり、**順に連結すると `.asm` の j 語と完全に一致した**。
>
> フィールドの境界は CSV から自動で得られる。残る作業は、意味が未確定の欄を確認することと、往復検証だけ（WP01）。
> 下の予備実験の記録は経緯として残しておく。

## 目的

PE 命令語（`j`、426bit）のビット割り当ては、SDM にも wogikaze/mncore にも記載がない。
Lean の README にも「全 426 ビット命令のデコーダはない」とある。
公式アセンブラ `assemble3` を差分オラクルとして使い、ブラックボックス解析が成り立つかを試した。

## 手順

`tools/probe_bits.sh` を WSL で実行する。

```
wsl -d Ubuntu -- bash /mnt/c/wgkz/nano20k/mncore/tools/probe_bits.sh
```

- 各ソース行を `assemble3 --instruction-mode flat` でアセンブルする。
- 先頭の `j` 語について、基準行（`lpassa $lm0v $ln0v`）とのビット差分を出す。
- ビット番号は文字列の左端を 0 とする（MSB が先頭と仮定しているが、未確認）。

## 結果

| ソース | 基準と異なるビット | 解釈 |
| --- | --- | --- |
| `lpassa $lm8v $ln0v` | 86, 290, 350, 410 | 入力 LM0 アドレスの bit3。**4 サイクル分のアドレスフィールド**に 1 ビットずつ（cycle0 だけ離れた位置にある。cycle1〜3 は 60bit 間隔） |
| `lpassa $lm16v $ln0v` | 85, 289, 349, 409 | 同じ 4 フィールドの bit4（1 つ上位側）。アドレスは連続したビット列で、左が上位 |
| `lpassa $lm0v $ln8v` | 107, 302, 362, 422 | 出力 LM1 アドレスの 4 フィールド |
| `ipassa`（`lpassa` との比較） | 146 | 精度・語長のフィールド |
| `iinc` | 146, 148 | opcode / 精度は 140〜150 付近 |
| `iadd $lm0v $lr0v $ln0v` | 146, 148, 150, 159–161, 262, 321, 381, 382 | 第 2 入力（GRF0 = `$lr`）の選択と、4 サイクル分のアドレス |
| `nop` | 20 ビット | nop は専用の符号。ALU 関連のビットが一斉に変わる |
| `lpassa …;fvadd $lr0v $ls0v $nowrite` | 65, 117, 118, 128, 136–143, 262, 280, 321, 339, 381, 382, 399, 400 | MAU-calc グループのフィールドは、ALU とは別の領域にある |

## わかったこと

- フィールドはきれいに分かれている。オペランドのアドレスは連続したビット列で、サイクルごとに別の位置にある。
  1 ビットだけ変えたプローブで、位置と重み（上位・下位の方向）が特定できる。
- 複数のグループ（ALU と MAU）は別の領域を使っている。`imm` と LM0 アドレスのように、フィールドを共有するものもある（`research/architecture.md` §2）。
- 以上から、**自動プローブで `fields.yaml` を作る方針は成り立つ**と判断した。

## P1 でやること

1. 文法の列挙: SDM 3.6 の命令式とオペランドの文法から、各要素を 1 つずつ変えたソースを自動生成する。
   ベースは `proofs_lean/scripts/check_isa_parser_bounds.py` と、`vsm.rs` のパーサにある語彙を使う。
2. ビットの帰属: 各変化が影響するビット集合を求め、フィールド（位置、幅、符号化）を推定する。
   アドレスや即値は値を掃いて線形性を確認する。enum は全値の表を作る。
3. 未使用ビットと固定ビット: 全プローブで変化しないビットを「定数」として記録する。
   定数のうち 1 になっているもの（例: 38、40、63、136〜144 など）の意味は、後から割り当てる。
4. MV 語（82bit）も同じ手順で調べる。サイズは `n/16` を 11bit で持つことがわかっている（`architecture.md` §3）。
5. 往復検証: 手元の全 `.vsm` について「アセンブル → Python でデコード → VSM 文字列に戻す → 再アセンブル」を行い、ビット単位で一致させる。
   一致しない語は「未知」として一覧にする。

## 注意

- ビット番号の向きは、出力文字列の先頭を 0 とした仮のものである。HW の実装では、426bit を MSB-first の 1 本のベクタとして扱えば問題ない。
- `assemble3` は Ubuntu 22.04 用の x86-64 ELF で、WSL の `~/wgkz/mncore/judge/judge-py/mncore2_emuenv/` にある。バイナリは再配布しない。
