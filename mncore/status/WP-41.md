## 要約

- **`hello.py`**: 1 コマンドで、公式の hello_world を assemble3 でアセンブルし、公式エミュレータで正解を作り、要るビットストリーム（MAU、M2aR）を用意し、`mnrun` で実機（語 0〜3 を MAU、4〜8 を M2aR、状態をホストが引き継ぐ）で実行し、DRAM を文字列で表示する。**実機の出力は DRAM n0 = `48656c6c6f2c2077 6f726c64212afe00` = "Hello, world!"、公式エミュレータと一致、全体 9.2 s**（うちビットストリームの書き込み 2 回 6.8 s）。
- **`fizzbuzz.py`**: `23.fizzbuzz-pe` の公式の解答を L1MAU（4 PE）で実行し、LM1 を FizzBuzz の文字列で表示する。既定の入力は 1, 2, 3, ...（テストケースと同じ並びで作る）。**実機の出力は 1〜32 の FizzBuzz、公式 16/16 長語・Python 32/32 個が一致、全体 8.3 s**。問題のテストケース（乱数）でも一致。
- **64 PE の FizzBuzz**: V64（WP34 の仮想 PE、整数 ALU だけ）で動く FizzBuzz 系の本がコーパスになかったので、**整数 ALU だけの解答（27 語、`programs/fizzbuzz_int.vsm`）を書き**、`fizzbuzz.py --program int` で実行した。**実機の出力は 1〜512 の FizzBuzz（64 PE）、公式 256/256 長語・Python 512/512 個が一致、全体 15.1 s**。
- **公式ツールがない経路**（`--no-official`）: コミットした公式アセンブラの出力と、記録した公式エミュレータの出力で、同じ結果と照合を出す。実機で hello / fizzbuzz / fizzbuzz int の 3 つとも PASS。
- 実機のログは 10 本（`mncore/demo/logs/`）、値の食い違い 0。ボードのロックを守り、SRAM にだけ書いた。最後は LED の方針の L1MAU を書いた状態で残した。

## 判断と理由

1. **FizzBuzz の表示は LM1 から作った。** 指示書は「DRAM の出力を文字列として」だが、実機で最後まで動く `23.fizzbuzz-pe` は、出力が DRAM ではなく各 PE の LM1（0xFFFFBBBB / 0x0000FFFF / 0x0000BBBB か元の数）である。LM1 の値を FizzBuzz / Fizz / Buzz / 数に読み替えて表示した。DRAM に "1\n2\nFizz\n…" を書く `20.fizzbuzz/answer.vsm` は、指示書どおり WP39 の後に回した。
2. **既定の入力は 1, 2, 3, ...（`--input seq`）にした。** 問題のテストケースは乱数（1〜2^15）で、FizzBuzz の並びとして読めない。テストケースと同じ並び（L2B、L1B、MAB、PE、長語、語の順）で 1〜32768 を置いたテストケースを作り、公式エミュレータにはチップ全体（4096 PE）を、実機には実装した PE の分を流す。4 PE では 1〜32、64 PE では 1〜512 になる。問題のテストケースも `--input testcase` で実行して照合した。
3. **64 PE で動く FizzBuzz の本はコーパスになかったので、整数 ALU だけの解答を書いた。** V64（WP34 の仮想 PE）は整数 ALU だけを持つ。コーパスの FizzBuzz 系（`20.fizzbuzz` の 3 本、`23.fizzbuzz-pe` の 4 本、mncompile の 2 本、`fizzbuzz-delivery` の 5 本）は、どれも MAU / FP ALU / L1BM / L2BM / MV のいずれかを使い、V64 / V64L1 では動かない。`programs/fizzbuzz_int.vsm` は 27 語で、公式エミュレータで 1〜32768 と問題のテストケース（各 32,768 個）が Python の FizzBuzz と一致することを確かめてから、実機で動かした。
4. **公式ツールがない経路**: 公式アセンブラの出力（`programs/*.main.asm`）をコミットし、テストケースの `d set` / `d get` 行と組み合わせる（テストケースの解答の後ろの部分が `d` 行だけであることを確かめる）。公式ツールがあるときの入力（`official.asm`）と同じ IMEM 語・同じ `d` 行になることを確かめた。照合には記録した公式エミュレータの出力を使う（なければ照合を省く）。
5. **デモは毎回ビットストリームを書く**（`--reuse` で、FPGA に入っているメンバーが最初の区間のものなら省く）。1 コマンドで「用意、書き込み、実行」を見せるため。`mnrun.Board` の `ensure` だけを無効にした派生クラス（`FreshBoard`）を demo の中に置いた。
6. **ボードのロック**: 各スクリプトが `C:\wgkz\nano20k\mncore\.board.lock` に「WP41 demo <スクリプト> 時刻」を書き、終わったら消す。ほかの作業のロック（2 時間以内）があれば止まる。同じ WP 番号のロックは自分のものとして扱い、消さない（複数のデモを続けて回すとき用）。ロックのディレクトリがない環境（ほかの PC）ではロックしない。
7. **ビットストリームはこの worktree で作り直した**（main の `f2d4918` の RTL）。M2a / MAU / L1MAU は種 1 で 27 MHz を満たした。M2aR は今の RTL では種 1、2、4、5 が 26.1〜26.7 MHz で届かず（WP38 では種 2 が 27.72 MHz で通った）、種 3 が 28.15 MHz で通った。demo の自動ビルドは M2aR を種 3 から試す（`demolib.SEEDS`）。V64 はデザイン ID 0x06 の今の RTL で作り直した（種 1、コア 39.9 MHz、LUT4 47 %）。WP34 / WP38 の worktree に残るビットストリームは使っていない。
8. M2aR の種 3 が通った時点で、並列に回していた種 6〜11 のビルドを止めた（`build/M2aR_s*` に途中の生成物が残るが git 管理外）。

## 未解決の点

1. **`20.fizzbuzz/answer.vsm`（DRAM に "1\n2\nFizz\n…" を書く FizzBuzz）は扱っていない**（指示書どおり WP39 の後）。WP38 の組では語 9 で E_RANGE（LM 256）、その先も語 19 が FP2 + L1BM + MAU を同じ語で使うので、今の組では最後まで動かない。WP39（全機能を 1 本に）か、仮想 PE と MAU / FP ALU の組み合わせが要る。
2. **`programs/` に公式ツールの出力をコミットした**: 公式アセンブラの出力（`*.main.asm`、3 本、計 19 KB）と、公式エミュレータの出力の一部（`*.official.ndmp`、5 本、各 256 行以下）。公式のバイナリそのものではなく、公開済みの問題に対する出力で、`mncore/tools/mnisa/tests/data/*.asm` や `mncore/tools/golden/testdata/*.official.dmp` と同じ扱いにした。ただし、WP42a の「公式の出力の扱い」がユーザーの判断待ちなので、公開しない判断になったら `programs/*.official.ndmp` を消す（照合は Python の FizzBuzz と問題文の "Hello, world!" だけになる）。`*.main.asm` も消すなら、公式ツールがない経路は使えなくなる。
3. **M2aR の余裕が小さい**: 今の RTL で試した 5 種のうち 4 種（種 1、2、4、5）が 27 MHz に届かず、通った種 3 も 28.15 MHz。RTL が少し変わると通る種が変わる。WP39 の後に作り直すときは、種を並列に試す必要がありうる（README の「所要時間」）。
4. **64 PE で動くのは整数だけの解答だけ**: 公式の解答（MAU、L1BM）や `20.fizzbuzz` を 64 PE で動かすには、MAU / FP ALU / L2BM / MV を持つ仮想 PE の構成が要る（WP34 の見積もりでは載らない）。
5. 64 PE の `d set` / `d get` は 1 行ごとに要求と応答を往復するので 3.2 s かかる（`mnhost.execute_program` の動き。`mnhost` は変えていない）。
