### 仮想 PE の構成（`mn_core` VPE = 1）

```
brd_host_if ── mn_core ─┬─ 命令メモリ、順序制御（WP37 のまま）
                        ├─ mn_vpe ─┬─ mn_mab（4 PE の時分割データパス、WP30。vm = いまの仮想 MAB）
                        │          │    └─ mn_mab_mem VPE = 1 ── mn_vpe_store（GRF0 / GRF1 / LM0 / LM1 → SDRAM）
                        │          ├─ mn_vpe_ctx（文脈: T / $omr / $mb・$nb / $aluf / $mauf ⇄ SDRAM）
                        │          └─ ホストエンジン（RUN の外: PE の空間 ⇄ SDRAM）
                        ├─ mn_l1bm（N_MAB の MAB、BS = 1: バッファを BSRAM に）── cur_mab = vm
                        ├─ mn_l2bm、mn_mv（M2 = 1、L2MV = 1 のとき。WP37 のまま）
                        └─ mn_vpe_arb（MV と仮想 PE）── sd_* ── sdr_bus64（ボードのトップ）── SDRAM
```

- **PE の状態はすべて SDRAM**（下の配置）。データパスは 1 MAB（4 PE）分の文脈の作業用の写し（`mn_pe_lsu` NPE = 4 の T / OMR / BAR、`mn_pe_core` のフォワーディングレジスタ）だけを持つ。LM / GRF は写しを持たず、`mn_vpe_store` が `mn_pe_lsu` のストアの要求をそのまま SDRAM に出す（契約 §6 の内部のメモリバス。`sdr_bus64` は順に答える）。BSRAM は PE の状態には使わない（作業 1 の「BSRAM はキャッシュ」は採らなかった: 判断と理由 2）。
- **1 語の実行**（`mn_vpe`）: MAB m = 0〜N_MAB−1 の順に、文脈の読み込み → MAB m の 4 PE で語を実行（`mn_mab`、vm = m）→ 文脈の書き戻し。読み込む・書き戻すのは語が使うものだけ（`mn_pe_core` の `cx_use`: T を読む / 書く、`$omr<imr>` を読む、`$omr<omr>` を書く、`$mb` / `$nb` を読む（LM のアクセス）/ 書く、`$aluf` / `$mauf` を読む / 書く。書き戻すのは読み込んだものか、4 サイクルとも書かれるものだけ）。`VPE_CXALL = 1` は T / BAR / `$aluf` / `$mauf` を毎回すべて動かす比較用。
- L1BM / L2BM のユニットの start（`ugo`）は MAB 0 のパスで出し、commit は最後の MAB の後（WP37 の順序のまま）。L1BM の PE ⇄ L1BM の項は `cur_mab` の位置に入る。
- **停止**（契約 §3）: E_UNSUPPORTED は語の性質なので MAB 0 の検査だけのパスで見つかる（何も書く前）。MAB 1 以降は、データのため（`xchk`: msl / msr / bfn / bfe、行列 MAU）でなければ検査だけのパスを省く（`nochk`）。LM_AW = 11 では LM / GRF の範囲外は起こらない（番地は 11bit で折り返す）。LM_AW < 11 かつ N_MAB > 1 で LM を使う語は、先に全 MAB で検査だけのパス（`chk_only`）を行い、**64 PE のどれが範囲外でも、どの PE も書く前に E_RANGE で止まる**（unit `vpe/m64r`）。
- **ホストの口**（RUN の外）: 空間 0x01〜0x05、0x10、0x11 と新しい 0x12 `$aluf` / 0x13 `$mauf`（8 長語、2c + k）は SDRAM を直接読み書きする（ホストエンジン）。位置は `n0c0b0m<m>p<p>`（m < N_MAB）。マスクと範囲は `mn_pe_lsu` のホストの口と同じ（LM / GRF は 32bit レーン、T の MSB 側の長語は 16bit レーン、OMR はバイト、エントリ 0 は ffff を読み書き込みは無視、BAR は 12bit）。
- **リセット**: `SDCLR = 1` で DRAM、PDM（M2）と VPE 領域を 0 にする（公式の初期状態）。`CLEAR`（PE のホストの口からの消去）は VPE では使わない。
- 行列レジスタ（MAT）は N_MAB = 1 のときだけ置ける（16 MAB の構成では MAT = 0: 行列の語は E_UNSUPPORTED）。

**SDRAM の配置**（長語アドレス。WP33 の DRAM / PDM の後ろの空き 0xA0000〜0xFFFFF）:

| 範囲 | 大きさ | 内容 | アドレス |
| --- | --- | --- | --- |
| 0xA0000〜0xA7FFF | 2^15 | GRF0 / GRF1 | `GRF_BASE \| {pe[5:0], g, a[7:0]}` |
| 0xA8000〜0xA8FFF | 2^12 | 文脈（PE ごとに 64 長語） | `CTX_BASE \| {pe[5:0], slot[5:0]}` |
| 0xA9000〜0xBFFFF | | 空き（命令の先読みなどに） | |
| 0xC0000〜0xFFFFF | 2^18 | LM0 / LM1 | `LM_BASE \| {pe[5:0], l, a[10:0]}` |

`pe` = {MAB m, PE p}。文脈のスロット: T 0〜7（2c + k）、`$mb` 8、`$nb` 9、`$omr<e>` 16 + e、`$aluf` 32〜39、`$mauf` 40〜47。64 PE × (LM 2048 × 2 + GRF 256 × 2 + 64) 長語 = 2.3 MiB。

## 判断と理由

1. **`mncore/rtl/l1bm/mn_l1bm.v` にパラメータ `BS` を足した**（担当の一覧にない WP31 のディレクトリ）。16 MAB の L1BM ユニットのソースバッファ・`$lbf`・`$lbi` を LUT RAM に置くと RAM16SDP4 が 1,536 個要り、デバイスの 648 個を超える。BSRAM（同期読み出し）に置く版を `BS = 1` とし、既定 0 は従来と同じ回路にした（`mn_core` は N_MAB > 1 のときだけ `BS = 1`）。`tb_l1bm` に BS = 1 の環境（N_MAB 16、RRN 1）を足し、WP31 の直接試験 96 本がそのまま通る。`mn_pe_core` は `LBS = 1` で `$lbf` の読み出しを 1 クロック待つ。
2. **LM / GRF は SDRAM を直接読み書きし、BSRAM のキャッシュは作らなかった**（作業 1 の「BSRAM はキャッシュ」）。MAB を入れ替えるたびに LM を写すと、1 語あたり 16 MAB × 4 PE × LM 2048 × 2 長語を動かすことになり、語の実行より桁違いに遅い。語が実際にアクセスする長語だけを SDRAM に出す方が速く、正しさの検証もやさしい。タグ付きのキャッシュは速くする工夫として後に回した（申し送り）。文脈（T など 27 項目 × 4 PE）は語が使うものだけを入れ替える。
3. **64 PE の構成の E_RANGE**: 契約 §3 の「4 PE（時分割）では、どれかの PE が範囲外なら、どの PE も書く前に E_RANGE で止まる」を 64 PE に広げた。LM_AW = 11（既定）では範囲外が起こらないので費用はない。LM_AW < 11 の 64 PE 構成（試験用の `vpe/m64r`）は、LM を使う語ごとに 16 MAB の検査だけのパスを先に行う。
4. **64 PE の回帰のプローブを小さくした**（`run.py` の probe `vpe`）。WP37 のプローブを 64 PE と LM 2048 に広げると 1 本あたり約 31 万長語になり、公式の実行も RTL のダンプも遅すぎる。LM の全体（2048 × 2）は MAB 0 と MAB 15 の PE だけで読み、ほかの PE は LM0 / LM1 の 0〜255 を読む。GRF、T、OMR、L1BM、L2BM、DRAM の範囲は WP37 と同じ（N_MAB ≤ 2 は全 PE で LM の全体）。LM の後半を使う本（FizzBuzz の解答など）は MAB 0 の PE で確かめられる。
5. **`L2MV = 0`（L1BM ユニットだけ）を足した**。64 PE に L1BM / L2BM / MV を全部載せると LUT 換算 77 % で予算（75 %）を超える。L2BM と MV を外した V64L1 で、L1BM の 16 MAB の縮約を実機で確かめる。L2BM の部分のある語は E_UNSUPPORTED `l2bm_lwrite`、m 語は E_UNSUPPORTED（m の欄 0）。
6. `tb_core.v`（WP20 の tb）を VPE の unit と回帰でも使うので、define と `H` / `F` / `+stopfail` を足した。既存の台本の動きは変えていない。
7. **公式の実行**: 64 PE の直接試験（`gen_vpe.py`）は 4096 PE の公式を実行し、L1B n0c0b0 の 64 PE と L1BM を切り出した（データが L1B の中で閉じるので契約 §3 (b)）。公式は `emu_batch.sh` から WSL で呼ぶだけで、バイナリはコミットしていない。
8. **行列レジスタ（MAT）は N_MAB = 1 だけ**。MAB ごとの行列レジスタ（X / Y の 2 面）を文脈として入れ替えると 1 語の費用が大きく、資源も足りない。64 PE の構成は MAT = 0 で、行列の語（`?mwrite` など）は E_UNSUPPORTED（64 PE の回帰の E_UNSUPPORTED 280 本はすべて `?mwrite`）。
9. **ホストの PE 空間は SDRAM を直接読み書きする**（ホストエンジン）。データパスの作業用の写しは、語ごとに文脈エンジンが読み込むので、RUN の外で写しを更新する必要がない。
10. **縮小 Rust と食い違った 13 本（FizzBuzz の系統）は「mismatch」のまま表に残した**（契約 §1。分類を書き換えていない）。食い違いの場所を語ごとの比較で突き止め、その演算を公式・縮小 Rust・RTL で単独に実行して、公式 = RTL を確かめた（2 の (a) の注）。
11. **変異の試験の見直し**: `mn_vpe_store` の「読み出しの応答をそのチャネルへ」の変異は、`mn_pe_lsu`（RBS = 1）が 1 つのメモリの読み出しを全部受け取ってから次のメモリに移るので、どの台本でも結果が変わらない（等価な変異）。外して理由を `mutate.py` に書いた。MV と仮想 PE の調停の変異は既存の台本では見つからなかったので、MV の転送中に 64 PE が LM / GRF を使う試験 `mv_overlap` を足した（`fixed/m64.scr` の先頭。`gen_vpe.py` で全部を作り直したときと同じ並び）。
12. **実機で回す本**: V64（ユニット・MAU・FP ALU なし）は整数だけの PE の本 39 本、d set / d get だけの本 20 本、LM の番地が 256 以上か実行時に決まる本 4 本（`list_v64.txt`、63 本）。V64L1 は整数と L1BM の本 37 本（`list_v64l1.txt`）。FizzBuzz の解答は MAU・FP ALU・L2BM・MV が要るので、実機では回していない（作業 5 の但し書き。RTL シミュレーションまで）。

## 未解決の点

1. **64 PE の構成に行列レジスタがない**: 行列の語（`?mwrite` など）は E_UNSUPPORTED（64 PE の回帰で 280 本）。MAB ごとの行列レジスタを文脈として入れ替えるか、行列の語だけを 1 MAB の構成で実行する（WP38 の切り替え）かは決めていない。
2. **速さ**: 1 語あたり、BSRAM の 4 PE（M2）の 1.54 倍（1 MAB）、9.2 倍（64 PE。1 MAB あたりでは 0.58 倍）。時間の 2/3 は LM / GRF のオペランドの SDRAM の待ち、1/3 は文脈の入れ替え。キャッシュや読み出しの重ね合わせは入れていない。
3. **64 PE のビットストリームに MAU / FP ALU / L2BM / MV は載らない**（LUT。6 の見積もり）。FizzBuzz の解答は実機では動かしていない（作業 5 の但し書きのとおり RTL シミュレーションまで: 16 MAB で pass c、DRAM の 64 長語が公式と同じ）。
4. **縮小 Rust（viz/core）の fvfma の誤り**（y に `e` のとき MSB 側のレーンが 1 ULP 違う。2 の (a) の注）。公式は RTL と同じ。WP06 の担当で直すか、既知の食い違いとして表に残すかを決める必要がある。直すまで、1 MAB の回帰で FizzBuzz の系統 13 本が mismatch と出る（16 MAB では出ない）。
5. **実機の回帰は 100 本**（V64: 整数の本と d set / d get の本 63 本、V64L1: L1BM の本 37 本）。MAU / FP の本は、それを載せた 64 PE のビットストリームがないので回していない。
6. `hwrun.py` の「as the RTL simulation」は、同じ構成の RTL の表（`build/vpe16_lm11/results_<tag>.tsv`）が先にないと 0 と出る。今回は実機の後に RTL の表を作って照合した（100/100 同じ）。
7. 複製規則（REPLICA = 1）での 64 PE の回帰は回していない（16 MAB では複製は L2BM の存在しない L1B にだけ効く）。
8. 64 PE の回帰は iverilog で 52,000 秒（CPU 時間）かかる。全構成を何度も回すなら、並列度を上げるか verilator に移すことを考える。

## 契約変更の要望

1. **§3 縮小トポロジ**: `N_MAB` = 16 と `LM_DEPTH` = 2048 を仮想 PE の構成（`mn_core` VPE = 1）で使えるようにした。`LM_DEPTH` は構成ごとの値（INFO の空間 1 / 2 の深さ）とし、「4 PE（時分割）では、どれかの PE が範囲外なら、どの PE も書く前に E_RANGE で止まる」を「時分割・仮想 PE の構成では、実装したどの PE が範囲外でも、どの PE も書く前に E_RANGE で止まる」に広げる（判断と理由 3）。
2. **§3 SDRAM の配置**: 「0xA0000〜0xFFFFF は空き」を、0xA0000〜0xA7FFF GRF、0xA8000〜0xA8FFF 文脈（PE ごとに 64 長語）、0xC0000〜0xFFFFF LM（仮想 PE。`rtl/vpe/README.md`）、0xA9000〜0xBFFFF 空き（命令の先読みなど）に。`SDCLR` は RESET の後に仮想 PE の領域も 0 にする。
3. **§7 デザイン ID**: 0x05 = `mn_top_vpe`（仮想 PE。トポロジ 1/1/1/N_MAB/4、フラグは `mn_top_m2` と同じ。M2 = 1 で空間 6〜9、L2MV = 0 では 6 だけ）。
4. **§7 空間 ID**: 0x12 `$aluf`、0x13 `$mauf`（PE ごとに 8 長語、2c + k。仮想 PE の構成のホストの口と文脈エンジンが使う）。WP38 の状態の引き継ぎにも使える。INFO に設計固有の空間を載せる方法は未定のまま（`mnhost` は使わない）。

## 次の WP への申し送り

**WP40（統合・適合試験）**

- 仮想 PE の回帰: `run.py --vpe 16`（64 PE、811 本。iverilog 10 並列で約 1 時間 40 分）、`run.py --vpe 1 --m2`（LM 2048、247 本。3 並列で 41 分）。`--lm-aw 8..11`、`--vpe-units 0 / 2`（実機の V64 / V64L1）と `--define TB_FPALU=0` などで実機の構成になる。公式・縮小 Rust の結果は `build/vpe<N>_lm<A>/` にキャッシュ（`--skip-official --skip-rust`）。表の列 `vpe`（文脈の読み込み / MAB の開始 / MAB のパス / 書き戻しのクロック、検査だけのパス、SDRAM の要求数）と `seconds`。
- 分類は WP37 と同じ（pass b / pass c / E_RANGE as rust）。64 PE で値の食い違い 0。1 MAB の FizzBuzz の系統 13 本の mismatch は縮小 Rust の fvfma の誤り（未解決 4）。全構成の表では注記するか、縮小 Rust を直した後に回し直す。
- 64 PE の E_UNSUPPORTED 280 本は行列の語（MAT なし）。合格率の表では「64 PE の構成は行列なし」として扱う。
- 64 PE の公式・縮小 Rust・RTL の比較はプローブを小さくしてある（判断と理由 4: LM の全体は MAB 0 と 15 だけ）。
- 変異の試験は `mncore/sim/tb/vpe/mutate.py`（23 種）。tb_core の `+stopfail` で検出した変異は最初の不一致で止まる。

**WP41（FizzBuzz / MNIST のデモ）**

- FizzBuzz の解答は **LM 2048 が要る**（LM0 の番地 2178 語）。仮想 PE で最後まで動く（RTL）。**16 MAB（64 PE）なら DRAM の 64 長語が公式と同じ**（"1\n2\nFizz\n4\nBuzz\n…\n16\n17\n" など。2 の (b)）。全部の出力（4096 長語）は 64 L1B が要る（ゼロ規則では残りは 0）。
- 実機に載せるには MAU、FP ALU（`fmin` / `fmax` / `ffloor` / `fftoi` を使うので FPALU 1）、L1BM / L2BM / MV、LM 2048 が要る。1 本には載らない（6 の見積もり: 1 MAB + MAU（FPALU 0）70.9 %、1 MAB + ユニット 73.3 %、1 MAB + MAU + FPALU 1 は 82.1 %）。WP38 の自動切り替えと組み合わせるなら、仮想 PE の構成どうしの切り替えで、PE の状態（LM 2048 × 2 など）が SDRAM にあることを使える: SDRAM が SRAM の書き直しをまたいで残るか（WP38 が確かめる）と、`SDCLR`（コンフィグ直後と RESET で VPE 領域を 0 にする）を切り替えのときだけ止める口が要る。残らないなら、ホストが 1 MAB あたり約 18,700 長語（4 PE × (LM 2048 × 2 + GRF 256 × 2 + 文脈 64)）を引き継ぐ。
- 64 PE の構成（V64 / V64L1）は 1 語あたり約 2,700〜3,000 クロック（実機。27 MHz で 1 秒に約 9,000 語）。

**そのほか**

- `rtl/core/mn_core.v` の変更は `VPE = 0` の構成の動作を変えていない（既存の回帰と unit がクロックまで同じ）。`mn_core` のホストの口の形（`mw_*` / `mr_*`、空間 ID の扱い）は変えず、仮想 PE の空間（0x12 / 0x13）を `is_pe_space` に、64 PE の位置を `is_pe_loc` に足しただけ。WP38 が `rtl/core/` にデバッグの口を足していれば、マージではこの 2 つの関数とポートの並びの付近を見てほしい。
- `mn_top_vpe` の INFO のトポロジは 1/1/1/N_MAB/4。`mnhost` の `Topology` はそのまま 64 PE の位置を作る（`hwrun.py`）。
