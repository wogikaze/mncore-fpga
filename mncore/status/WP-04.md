### ピン割り当て（出典）

出典は Sipeed 公式の例 [sipeed/TangNano-20K-example `uart/src/top.cst`（コミット d8e3cfb）](https://github.com/sipeed/TangNano-20K-example/blob/d8e3cfb86ac19966244cc99d12c1da84d7ba4199/uart/src/top.cst)

同じリポジトリの `picorv32/src/fpga_project.cst` も `ser_tx` を 69 に置いている。Sipeed の wiki のページには番号の記載がなかった。
実機で双方向の通信ができたことで、割り当てが正しいことも確認した。

### プロトコルの要点（詳細は PROTOCOL.md）

- フレーム `0xA5 | cmd | len u16le | payload | crc8`。CRC は CRC-8/SMBUS（多項式 0x07、初期値 0）。応答は `cmd|0x80` で、先頭が状態コード。
- コマンド: `PING` 0x01、`INFO` 0x02、`WR_IMEM` 0x03、`WR_MEM` 0x04、`RD_MEM` 0x05、`RUN` 0x06、`STATUS` 0x07、`RESET` 0x08、`SET_BAUD` 0x09。
- ペイロードは受信バッファ（2 KiB）に溜め、CRC が一致してから実行する。壊れたフレームはメモリを書き換えない。
- フレームの途中で 20 ms 途切れたら破棄して待機に戻る。CRC 不一致は `E_CRC` を返す。
- `SET_BAUD` は旧速度で OK を返してから切り替え、1 秒以内に正しいフレームが来なければ元に戻る。
- 命令メモリは space 0。1 エントリ 448bit（7 長語）で、`[447:446]` が種類（01 = `j`、10 = `m`）、`[425:0]` が `jw`（契約 §2 の向き）。
- `RUN` は開始の受理だけを返し、ホストは `STATUS` で終了を待つ。アーキテクチャ状態は RUN をまたいで保つ（`d get` の位置で RUN を分割できるようにするため）。

### 実機で分かった BL616 ブリッジの性質（PROTOCOL.md §7 に記載）

1. 連続して大量に FPGA → PC へ送ると、ブリッジ内に約 8〜10 KB たまった時点でバイトが落ちる（1M で約 28 KB、2M で約 12 KB、3M で約 10 KB の連続送信の後）。
   FPGA 側の計数は 0 のままで、PC 側で応答の CRC 不一致として現れる。ホストの流量制御（未受信の応答を 6300 バイト以下）で解消した。
2. PC から Ctrl-X（0x18）と Ctrl-C（0x03）を**1 バイトずつ別の write で**送ると、BL616 は自分のシェル（`TangNano20K />`）に入る（Sipeed の unbox ガイドの手順）。
   フレームの中に 0x18 0x03 0x0D が並んでいても入らないことを実機で確かめた（`PING` のペイロード、64 KiB の書き込みデータ）。
3. **シェルに入ったあとは `choose uart` でも FPGA → PC の中継が戻らない。** BL616 の `reboot` で戻る。
   作業中に一度、ロックを外していた間（19:26〜19:43）の後で中継が止まっていた（旧ビットストリームでも、WP05 のビットストリームでも無応答）。BL616 の `reboot` で回復した。
   原因は特定していないが、誰かがシェルに入ったことと症状が一致する。回復用に `mnhost.py bridge reboot` を用意した。

## 未解決の点

1. **BL616 ブリッジの制約（FPGA 側では直せない）。**
   - 4 Mbaud 以上は使えなかった（4M、5M、6M とも `SET_BAUD` 後の確認に失敗し、自動で元の速度に戻った）。
     Windows の FTDI 互換ドライバか BL616 のファームウェアが 3M までしか設定できないとみられる。
   - FPGA → PC の持続速度は約 70 KiB/s が上限で、2M や 3M にしても読み出しは速くならない。
     さらに、ブリッジに約 8〜10 KB 以上たまると FPGA → PC のバイトが落ちる。ホストツールは未受信の応答を 6300 バイト以下に保つことで回避している（PROTOCOL.md §7）。
   - 応答の遅延が 1〜11 ms あり、小さなコマンドの往復は 5〜12 ms かかる。`STATUS` のポーリングもこの単位になる。
     Windows のデバイスマネージャで COM6 の「待ち時間（Latency Timer）」を 16 ms から 1 ms に下げると改善する可能性があるが、システムの設定を変えるので試していない。
   - BL616 のシェルに一度入ると、`reboot` するまで FPGA → PC の中継が止まる。端末ソフトで Ctrl-X / Ctrl-C を押すと起きるので、ボードを使う全 WP に周知が必要。
2. **WP05 への影響の可能性。** 最後の確認で `mnhost.py bridge info`（シェルに入って `uart_info` を読み、`choose uart` で戻る版）を試したところ、「BL616 ブリッジの性質」の 3 の理由で中継が止まった。
   その直後（19:57:38）に WP05 がロックを取ったため、WP05 の `uartexp2`〜`uartexp4` の実行は中継が止まった状態だった可能性がある。
   - `bridge info` は最後に `reboot` するように直した（`choose uart` は使わない）。
   - ロックの空きを待って 2 回回復を試みた。20:02:51 の回では再起動の後も応答がなかった。
     20:04:12 の回では開始時点で中継が止まっており、BL616 の `reboot` → `board_test` の再書き込みで 1 Mbaud の `PING` が通った（20:04:32、ロック解放）。
   - WP05 も同じ時間帯に UART を調べていたようなので、WP05 の UART の結果は、この時間帯のものを割り引いて見てほしい。lead から WP05 に周知してほしい。
3. **`brd_host_if` の資源が大きめ。** UART と FIFO を含めて LUT4 換算で約 2,000、DFF 約 800、BSRAM 3 個（受信 FIFO、送信 FIFO、受信バッファ）。
   多くは 16〜32bit のカウンタと比較器、`INFO` / `STATUS` の応答を作るマルチプレクサ（約 300 LUT）。WP21 で LUT が足りなくなったら、FIFO を小さくする、`INFO` を簡略化するなどで減らせる。
4. **クロックの乗せ換えは未実装。** `brd_host_if` とコアは同じクロックで動かす前提。WP21 でコアを 27 MHz 以外にするなら、`rtl/board` に CDC の層を足す必要がある（契約 §6 で CDC は board と sdram の中だけ）。
5. **ndmp の細部は WP02 と未調整。** WP02 の変換器はまだなかったので、`mnhost.py run` の ndmp は次の解釈で出している（PROTOCOL.md §6）。
   - LM / GRF のアドレスは長語アドレス（単語アドレス / 2）。T は `2 × サイクル + (0: MSB 側, 1: LSB 側)`。
   - 単語アクセスの `d get`（`$m1` など）は、その単語を含む長語を 1 行で出す（公式のダンプは単語だけを表示する）。
   - 同じ位置を何度も `d get` したときは、重複した行をそのまま残して辞書順に並べる。
6. 実際のコア（`mn_core`）がまだないので、`.asm` の実行は RUN スタブと、全空間を TEST メモリに写す `--map-test` でしか確かめていない。
   `d set` / `d get` のアドレスと位置の変換は、公式エミュレータのダンプと一致することを確認した（実機の smoke test）。

## 契約変更の要望

1. **§7 のコマンド一覧に `INFO`（0x02）と `SET_BAUD`（0x09）を追加する。**
   - `INFO` はホストが命令メモリの深さ、実装トポロジ、空間ごとの深さ、FIFO の大きさを知るのに使う（縮小トポロジでの `d set` の展開に必要）。
   - `SET_BAUD` は速度の測定と運用に使う。確認がなければ 1 秒で元に戻るので安全。
2. **§7 の「初期は 1 Mbps」は維持し、運用は 2 Mbaud を推奨する。**
   2M はブリッジの誤差が +0.1〜0.2 % で、書き込みは 1M より速い。3M はブリッジが実際には 3.076 Mbaud で動くので、FPGA 側の分周を測定値に合わせる必要がある（ホストツールが自動で行う）。読み出しは速度を上げても速くならない。
3. **§7 に空間 ID と位置の符号化を載せる**（PROTOCOL.md §4）。WP14 / WP20 / WP21 の記憶のアドレスデコードがこれに従う必要がある。
   - 空間: 0 `IMEM`、1 `LM0`、2 `LM1`、3 `GRF0`、4 `GRF1`、5 `T`、6 `L1BM`、7 `L2BM`、8 `PDM`、9 `DRAM`、15 `TEST`。アドレスはすべて長語単位。
   - 位置: `loc = n<<10 | c<<9 | b<<6 | m<<2 | p`（実チップでの座標）。
4. **§6 に命令メモリのエントリ形式を載せる。** 448bit、`[447:446]` = 種類（01 `j`、10 `m`）、`[425:0]` = `jw`（`j` 語）、`[81:0]` = `m` 語。
   WP20 の `mn_core` はこの形式で取り出して振り分ける。
5. **§4 の例の `L1BM n0c0` は `L1BM n0c0b0` とするのがよい。** 公式エミュレータのダンプは `DEBUG-L1BM(n0c0b0,4)` の形で、L1BM の位置は b まで持つ。
   T のアドレスと、単語アクセスの `d get` の扱い（上の「未解決の点」5）も、WP02 と合わせて契約に書くのがよい。

  64 KiB の読み出しに約 1 秒かかる（読み出しは約 70 KiB/s が上限）ので、8 MiB 全域の照合は FPGA 内で行い、結果だけを UART で返すのが現実的。
- **WP02（ゴールデン）**: 上の ndmp の解釈を確認し、違えば知らせてほしい。`mnhost.py` の `long_words()` と `run_program()` を直す。
- ボードを使うときの手順: ロックを取る → `build.ps1 -Program`（SRAM に書く）→ `hwtest.py` → ロックを消す。ボーレートが分からなくなったら S1 ボタンでリセットする。どの速度でも応答がなければ `mnhost.py bridge reboot`（BL616 の再起動）を試す。
