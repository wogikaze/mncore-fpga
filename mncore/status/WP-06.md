### 使い方

```sh
cd third_party/mncore/viz/core            # 実行は WSL（下の「Windows で cargo test できない」を参照）
cargo run --release --bin sim_run -- --topology l2b=1,l1b=1,mab=1,lm=256,grf=256,l1bm=1024,l2bm=4096 prog.vsm
cargo run --release --bin sim_run -- --topology l2b=1,l1b=1,mab=16 --compare-full prog.vsm
cargo run --release --bin difftest_file -- --topology l2b=1,l1b=1,mab=16,lm=256 prog.vsm
```

- 仕様文字列のキー: `l2b l1b mab pe lm grf l1bm l2bm pdm dram`（メモリは長語単位、省略したキーは実チップの値、`pe` は 4 のみ）。値は 10 進、`0x` 16 進、`Ki` / `Mi` 付きも可。`full` または空文字列は実チップ。
- `sim_run` の出力: 1 行 1 長語 `<メモリ> <位置> <アドレス> <値16桁hex>`。名前とアドレスは `Sim::dump` のキーと同じ（`LM0 LM1 GREG0 GREG1 TREG OMR L1BM L2BM DRAM PIU`。LM / GRF は長語の先頭の語アドレス、L1BM / L2BM / DRAM / PIU は長語アドレス）。位置はチップ座標。`PIU` は PDM の値で、公式エミュレータの `d get $p`（DRAM を表示する）とは比べられない。
- 終了コード: 0 成功、1 実行時エラー、2 使い方・入力の誤り、3 E_RANGE、4 `--compare-full` で不一致。
- ライブラリ: `Sim::with_topology(Topology::parse(spec)?)`、`Topology::restrict(&full_dump)`。

### 縮小構成の意味（要約。正本は `docs/topology.md`）

契約 §3 との対応:

| 契約 §3 | 実装 |
| --- | --- |
| `N_L2B` / `N_L1B` / `N_MAB` / `N_PE` | `l2b` / `l1b` / `mab` / `pe`（4 固定） |
| `LM_DEPTH` / `GRF_DEPTH` / `L1BM_DEPTH` / `L2BM_DEPTH` | `lm` / `grf` / `l1bm` / `l2bm`（長語） |
| PE は n0c0b0m0p0 から順に割り当てる | L2B i は `n{i/2}c{i%2}`、各 L2B は b0〜、各 L1B は m0〜 |
| `$peid` などは実チップの値 | そのとおり。ダンプの位置もチップ座標 |
| 容量の外はトラップ（E_RANGE と語番号）、折り返さない | `ExecError::Range`。`RunError.word` が命令語番号 |

WP の指示による追加の規則:

1. 存在しない L2B / L1B / MAB（と、L2B を持たないグループの PDM / DRAM）への転送は捨てる。読み出しもしない。
2. 存在しないユニットから受け取る結合・縮約の入力は、値ゼロとする（単位元ではない）。
3. `l2bmr` の L1B 集合の外の L1B は、実チップどおり単位元を送る。集合の中で存在しない L1B はゼロを送る。
4. 容量の外: アドレスを実チップの大きさで折り返した後、縮小した容量以上ならエラー。存在するユニットへのアクセスだけを検査。書き込みマスクで止まる書き込みも検査。`d set` / `d get` / `r` も検査。

### 4. MV の DRAM 側の歩き方の修正（lead の追加依頼）

lead の連絡（WP02 の全件比較: 2b9e595 以降、MV の n128 転送が公式エミュレータと食い違う）を受けて、原因を確かめて直した。
上の「既定構成の回帰」で変更前から落ちていた 2 件が、この不具合だった。

- 公式エミュレータで、各グループの DRAM に別々の値（グループ g の長語 a に `(g << 16) | a`）を置いて測った（`scratchpad/mv_probe*.py`、サイズ 64 / 128 / 256）。
  - `mvb/n $d0 $lc0`: L2BM の `64 i + 16 g + k` ← グループ g の DRAM の `16 i + k`
  - `mvd/n $p0@0 $d2048`: グループ g の DRAM の `2048 + 16 i + k` ← PDM の `64 i + 16 g + k`。逆向き（DRAM → PDM）も同じ対応
  - `mvriiadd/n $lc0 $d0`: グループ g の DRAM の `16 i + k` ← L2BM の `64 i + 16 g + k` の縮約
  - `mvb4` / `mvr4`: `32 i + 16 c + k`（Rust と一致していた）
- 2b9e595 は、これらの DRAM 側を全グループ通しの番号 `4 i + g` のチャンク（`64 i + 16 g + k`）で歩いていた。64 長語の転送でもグループ 1〜3 の番地がずれるが、既存の問題はグループ 0 しか見ないので、128 長語以上で初めて表に出ていた。
- 修正: CPU（`mv.rs`）は各グループのチャンク `i` を使う。GPU のカーネル（`gpu/mv_kernel.cu` の mode 2 / 6 / 7 / 10）も同じ添字に直した。**GPU 側は、この PC に CUDA の GPU がないため実行していない。**
- 回帰テスト `mv::tests::group_spread_transfers_walk_each_group_dram_in_order`（上の測定値をそのまま固定）を追加。
- 間接参照（`$di`）の `mvb` / `mvd` / `mvr` は、同じく「各グループのチャンク i」に変えた（`mvp` と同じ考え方）。ただし、公式エミュレータで DAR を設定する探査がうまくいかず（`l2bmdars` の後も DAR が 0 のように振る舞った）、間接参照のこの 3 種は公式との一致を確かめられていない（変更前も未確認だった）。問題の中で間接参照を使うのは `mvp` だけで、そこは変えていない。

## 未解決の点

1. **MV の間接参照（`$di`）の `mvb` / `mvd` / `mvr` は公式との一致が未確認。** 上の「4.」のとおり、直接参照は公式で確かめて直したが、間接参照は公式エミュレータで DAR を設定する探査がうまくいかなかった。`docs/gpu-instruction-coverage.md` には「`nd` を省略した `$di` で公式エミュレータは DRAM にアクセスしない」という既存の観測もある。問題の中で間接参照を使うのは `mvp`（`nd` あり）だけで、そこは公式と一致している（変えていない）。
   - **GPU のカーネルの修正は未実行**（CUDA の GPU がない）。CPU と同じ添字にしただけだが、`check-conformance.sh --gpu` で確かめてほしい。
2. **proofs_lean のカタログ検査は変更前から失敗している。** CI の「Lean semantic proof audit」で動く `proofs_lean/scripts/catalog.py --check` は、master でも失敗する（CI では `judge/judge-py/judge.py` がなく FileNotFoundError、WSL ではその judge.py のハッシュが記録と違う）。
   - 今回の変更で `machine.rs` と `mv.rs` のハッシュも記録と変わる。proofs 側がカタログ（`coverage.json`、`evidence/isa-bounds/reference.json` の `tool_hashes`）を再生成するときに一緒に更新される。証拠のファイルには手を入れていない。
   - Rust と Lean の enum の対応を見る `check_issue_mirror.py` は topo-param でも pass する（`Mv` / `MvOperand` などの定義は変えていない）。
   - topo-param の push で、この workflow（`viz/core/**` の変更で起動）がブランチ上でも失敗として表示されるはず。原因は上の既存の問題。
3. **Windows では `cargo test` ができない**（変更前から）。GPU 用バイナリが Linux 専用のため。テストはすべて WSL で行った。
4. **判断に迷った点**（lead の確認がほしい。いずれも `docs/topology.md` に明記した）
   - (a) 「存在しないユニットからの結合・縮約はゼロ」を**値ゼロ**と解釈した（縮約の単位元ではない）。max / min / band / and の縮約では、存在しない入力のゼロが結果を変える（例: 負の値だけの最大値が +0 になる）。単位元に変える場合は `blocks.rs` の `src_of` / `read_l1` と `mv.rs` の `OffChip::read` の分岐を変えるだけで済む。
   - (b) 存在しないユニットへの転送は、読み出しも容量の検査もしない（存在するユニットへのアクセスだけを検査する）。
   - (c) **書き込みマスクで止まる書き込みも**範囲を検査する（アドレス生成の段階で判定する想定）。
   - (d) 契約の「語番号」は、止まった文の先頭の**命令語の 0 始まりの番号**とした（`RunError.word`）。メモリ・位置・アドレスはメッセージに入れた。
   - (e) **PE メモリの E_RANGE はステップの実行前に全 PE を PE 順に検査する**ので、同じステップの E_UNSUPPORTED などより先に報告される（並列実行でも報告が決定的になるようにするため）。FPGA の優先順位と合わせる必要がある。
   - (f) グループは「L2B を 1 つ以上持つもの」だけが存在するとし、PDM / DRAM / DAR もそこだけにあるとした。PDM / DRAM の容量（`pdm` / `dram`）は契約にないパラメータとして追加した。
   - (g) `N_PE` は 4 固定にした（`pe=4` 以外はエラー）。
   - (h) `d set` / `d get` が存在しない PE やユニットを指すときは、黙って無視する（エラーにしない）。容量の外は E_RANGE。
   - (i) アセンブラが拒否する不正なユニット番号（`l1bmm@16`、`l2bm@8` など）は、既定構成の挙動（配列外参照など）を変えないため、縮小構成でも特別扱いしていない。

## 契約変更の要望

1. **§3 に「存在しないユニット」の規則を追加する。** 現行の §3 には容量外の規則しかない。WP06 の指示書にある規則を、`docs/topology.md` の表の形で §3 に入れたい。
   - 存在しない L2B / L1B / MAB（と下記のグループ）への転送は捨てる。
   - 存在しないユニットから受け取る結合・縮約の入力は値ゼロ（単位元ではない）。
   - `l2bmr` の L1B 集合の外は単位元（実チップと同じ）、集合の中で存在しない L1B はゼロ。
   - `d set` で存在しない PE を指したら何もしない。`d get` は何も出さない（ホスト側ツールの扱いと一致させる）。
2. **§3 にグループと PDM / DRAM を追加する。** 「L2B を 1 つ以上持つグループだけが存在し、PDM / DRAM / DAR はそのグループにだけある」こと、容量のパラメータ `PDM_DEPTH` / `DRAM_DEPTH`（この実装の `pdm` / `dram`、長語、既定は実チップ）。WP33 が SDRAM に載せる容量を決めるときに必要になる。
3. **§3 の E_RANGE を具体的にする。**
   - アドレスは実チップの大きさで折り返してから、縮小した容量と比べる。
   - 存在するユニットへのアクセスだけを検査する。書き込みマスクで止まる書き込みも検査する。`d set` / `d get` / `r` も対象。
   - 「語番号」は、止まった文の最初の命令語の 0 始まりの番号（`nop/n` は n 語、`d` / `r` 行は 0 語）とする。この実装の `RunError.word`。
   - 同じステップに別のエラー（E_UNSUPPORTED など）があるとき、Rust Sim は PE メモリの E_RANGE を先に報告する。FPGA の優先順位も合わせるか、比較では停止理由の種類を問わないことにするか、決めてほしい。
4. **§3 の正解 (a) が使える範囲を明記する。** 「縮小構成の結果 = 全構成の切り出し」は、データの移動がトポロジに完全にそろったユニットの中で閉じる命令列に限る（MAB 内なら常に、L1BM 命令まで使うなら `mab=16`、L2BM まで使うなら `l1b=8,mab=16`、MV は一般に不可）。それ以外では (a) は WP06 の規則による値で、(b) とは一致しない。
5. **§1 の「Rust Sim は公式と全問題で一致を確認済み」に、どのコミットでの話かを書き添える。** master（e011bf9）では MV の不具合のため 146 件中 2 件が食い違う。topo-param の `5f0ceb1` 以降は 146 件すべて一致する（submodule の参照を更新すれば成り立つ）。
